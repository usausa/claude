# 確定した設計方針(テンプレ開発の決定記録)

> テンプレ自体の開発で確定した決定。**追記式**(覆すときは新しい項で上書きし、旧項に取り消し注記)。未決は [backlog.md](backlog.md)。

- **軽量フロー(Spec Kit 風)**: spec = REQ / plan / tasks。**DES(独立した恒久設計書)は廃止**(実装ミラー / 二重管理になりやすいため)。**plan / tasks は一時物**(Claude の Plan モード + タスクリスト)で、実装完了後に破棄し恒久文書化しない。
- **REQ = 軽量な spec(何を・なぜ)** として残す。決定は `ADR`、原則は `architecture`、現状仕様はコード + テスト + 生成物(OpenAPI 等)。
- **REQ 蒸留の機械化**: 「コード / テスト / ADR / architecture から復元できる情報は REQ に残さない」を `distill-req` skill + ワークフローの「意図の更新・蒸留」段として組み込み。判定基準は確定(個別の線引きは実運用で精緻化)。
- **skill の命名規約**: プラットフォーム固有の skill は `<platform>-xxx` 接頭辞(例: `blazor-playwright`。将来の MAUI 側は `maui-appium` 等)。(→ 2026-08「コンテキストは発火条件で配置する」で置換: 形態固有は skill でなく rules に置く)
- **外部 skill / MCP の扱い**: 標準 skill のみ同梱。外部(dotnet-skills 等)はプラグイン導入 / 上流 vendor せず、必要な要点を**日本語で蒸留した自前 skill** にして出典をリンクする(例: `blazor-playwright` は Aaronontheweb/dotnet-skills の playwright-blazor (MIT) を蒸留)。本プロジェクトの docs / conventions が常に優先。
- **二重管理の刈り込み(2026-07)**: `CLAUDE.md` は純 import shim(`@AGENTS.md` 1 行のみ)。全 md を「正 + 参照」に一本化 — コマンド早見表=workflow.md、レビュー観点=review-checklist、/trace 検出項目=trace command、DB 命名=data.md、警告抑制=coding-principles、PM 方針=docs/pm/README、ADR 手続き=/adr command(write-adr skill は内容・粒度のみ)、reference 生成の実行=/spec-sync(sync-docs-from-code skill は導入 + CI のみ)。README の commands / agents / skills 個名列挙は参照化(skill 追加時に列挙が腐った実績による)。機械強制済みのルール(SA1309 の `_` プレフィックス禁止等)は文書化しない。
- **許容する重複の基準**: (1) 実行物の再掲 = done.md の DoD 検査手順・done-check.ps1 のリマインド文(AGENTS DoD の実装)、(2) common 原則 → 形態別 doc の「〜の具体」節(原則→実装の階層で情報が増える)、(3) README の入口要約(README は置換可・非依存と宣言済み)、(4) AGENTS の常時 1 行 ↔ 詳細 doc(外部 skill 優先 ↔ conventions、秘匿値 ↔ security.md)。
- **形態は 3 系 + 2 層 doc(2026-07)**: `-Form maui|web|desktop`。architecture は「系の全般 doc + 技術固有 doc」の 2 層 — Web 系=`web.md`(全般)+`api.md`+`blazor.md`、XAML 系=`mvvm.md`(MAUI/WPF/WinUI 共通のレイヤ・MVVM 原則)+`maui.md`(MAUI 固有)/`desktop.md`(Windows 環境固有)+`wpf.md`(将来 `winui.md` を並置)。**UI 単位のサブオプション(-Ui 等)は設けない**: 系内の doc / skill は全部残す(未使用でも害が小さい: skill は関連時のみロード、doc は使う分だけ参照)。blazor-playwright skill は web のみ残す。**命名原則 = 系名(web / desktop / mvvm)は全般、技術名(api / blazor / wpf / winui)は固有**。winui.md は setup の採用リストに登録済みで、ファイルを置くだけで対応できる。
- **SDD モードは full|lite の 2 択(2026-07)**: `setup.ps1 -Sdd full|lite`(既定 full)。full=REQ を恒久化し蒸留。lite=仕様(SPEC)と実装プラン(PLAN)を `work/` の一時物とし、フロー = `/spec`(箇条書き→草案)→ 人レビュー & 承認 → `/plan`(チェックリスト・フェーズ分割)→ フェーズ実装 + `/verify` → `/review` → `/done` で**クローズ蒸留**(決定→ADR / 用語→glossary / 受け入れ条件→テスト名)して削除。lite は requirements / traceability / `/trace` / `distill-req` を撤去し `/spec`・`/plan`・`spec-close` を配置(`work/` は gitignore。→ 2026-08「作業フォルダは docs/work/ で git 管理する」で置換)。**`-PM` は full 専用**(1 feature ≒ 1 REQ が前提のため)。機構 = `<!-- sdd:xxx -->` マーカー 9 個(`.setup/sdd/xxx-{full,lite}.md`)+ workflow / done のファイル置換 + REQ 参照の中立化(意図=spec)。
- **worker 形態を追加(2026-07)**: `-Form maui|web|desktop|worker` の 4 系に。worker(Generic Host の常駐 Worker Service)は系 doc 1 本(`worker.md`: レイヤ・実行モデル・graceful shutdown・ホスティング)のみ — 「系の全般 + 技術固有」の 2 層は**分けるものがある系だけに適用**(YAGNI)。あわせて common 4 doc(errors / logging / data / security)のヘッダから形態別の例示列挙を外し「採用形態の doc の『〜の具体』を参照」に統一(形態が増えるたびに列挙が腐るため)。上位層の列挙(csharp-layered-feature)に Worker を追加。
- **保守情報はリポジトリ内で管理(2026-07)**: テンプレ保守の知識(原則・決定・検討事項・検証)は `.setup/maintenance/` に置き、Git で環境間同期する。外部(ローカルファイル・セッション memory)には正を置かない(ポインタのみ)。導線は AGENTS.md / README.md の `<!-- template-dev:start/end -->` ブロック(setup が除去)。理由: 複数環境での AI 保守には「リポジトリと一緒に移動する知識」が必要で、外部管理は同期されない弱点が実証されたため。
- **lite 基層化リファクタ(2026-07)**: SDD 機構を反転し **base = lite、full / PM は加算層**(`lite ⊂ full ⊂ full-pm`)とした。
  - **命名統一**: `/requirements`→`/spec`(agent も `spec`)、`/spec-sync`→`/reference`、`/cross-review`→`/review-cross`、`write-adr`→`adr-guide`、`distill-req` + `spec-close`→**`spec-close` 単一名**(full=蒸留して残す / lite=蒸留して削除、の層差分)、`REQ`→**`SPEC`**(`SPEC-NNNN`・`docs/spec/`。REQ 語彙は全廃)。**`/impl`**(フェーズ実装。`model:` は置かず、安価モデル切替は opt-in コメント)と **`/plan`** を基層コマンドとして新設(PLAN は全レベルで `work/` の一時物)。
  - **命名原則**: コマンドと補助 skill / agent は接頭辞グルーピング(`spec-*` / `adr-*` / `review-*`。`git-commit` 等の横断 skill は対象外)。コマンドは「ループ定常段(/spec /plan /impl /verify /review /done)」と「オンデマンド(/adr /reference /trace)」の 2 分類(オンデマンドは機能開発中に随時)。
  - **setup は単一排他 enum**: `-Sdd lite|full|full-pm`(既定 full)。`-PM` スイッチと lite+PM の実行時 throw を撤去(無効な組み合わせを構文的に表現不能へ)。
  - **機構**: base 本文に lite をインラインし `<!-- sdd:xxx:start/end -->` ブロックで囲む。lite=マーカー行のみ除去 / full=`.setup/sdd/xxx-full.md` でブロック置換 + `.setup/sdd/full/`(ミラーツリー)のファイル加算(spec・spec-close・done・workflow・work は上書き、trace・docs/spec・traceability は追加)。PM は従来どおり `.setup/pm/` 挿入 + 非採用時削除。経緯は [refactor-lite-base.md](refactor-lite-base.md)、最終形は [command-map.md](command-map.md)。
- **deny 領域の保守手順(2026-07)**: `docs/reference/**` の deny に保護されたファイルを保守で修正する必要があるときは、`settings.json` の deny を**一時解除 → 修正 → 即復元**する(差分で監査可能)。生成物ガードとしての deny は恒久維持。
- **データアクセスは EF Core を既定にしない(2026-08)**: ORM / データアクセス方式は用途で選定する(Micro-ORM・生 SQL も対等な選択肢)。原則の正は `common/data.md` に 1 行で置き、形態別 doc(`web.md` / `worker.md`)の「データの具体」はそこを参照する(形態ごとに ORM 名を列挙しない)。選定は `/adr` に残す。
- **ServiceDefaults プロジェクトを作らない(2026-08)**: Aspire の ServiceDefaults 相当(OpenTelemetry / ヘルスチェック / resilience / service discovery)は独立プロジェクトにせず、**Web アプリ本体(共有インフラプロジェクトがあればそちら)の `Application/` に拡張メソッドとして取り込む**。`AppHost` は残す。プロジェクト数を増やさず、既存の「組み立ては `Application/` へ」の層方針に一致させるため。
- **ホスティング API は `HostApplicationBuilder` 系に追随(2026-08)**: Worker のホスティングは `builder.Services.AddWindowsService()` / `AddSystemd()` を正とする(`UseWindowsService()` / `UseSystemd()` は旧 `IHostBuilder` 用)。
- **設定の注入形は明示しない(2026-08)**: `IOptions<Setting>` と設定実体のどちらを注入するかは要件次第。architecture doc では「設定は注入で受ける(注入形は要件で選定)」に留め、既定を決めない。
- **特定スタックを既定にしない(2026-08)**: architecture doc にはライブラリ非依存の規律だけを置き、特定ライブラリ(Smart 系等)前提の記述は本体に持ち込まない(選定は「プロジェクトで選定し `/adr`」の中立方針を維持)。特定スタック前提の方針(全 Singleton・Micro-ORM 標準・素の `T` 注入等)もテンプレ既定にしない。CancellationToken 伝播は現行既定(下位まで伝播)を維持し、非伝播はプロジェクト決定として `/adr` に残す。
- **コンテキストは発火条件で配置する(2026-08)**: アーキ規範は `.claude/rules/` の Path-Scoped Rules(`paths:` にマッチするファイルを読むと自動適用)。原本はカタログ `.setup/rules/` に全形態分を持ち、`setup.ps1` が共通 + 採用形態分をコピーする(コピー方式 = 原本保守中の誤発火防止と選定の一元化。旧 `docs/architecture/` は廃止)。skill はアプリ形態に依存しないフローのみ(.NET 依存は可。`blazor-playwright` skill は `blazor-e2e` rule 化)。`AGENTS.md` は参照だけを残して薄く保つ(Claude 専用に割り切る)。**paths を決められない規範は rule にしない**(発火しない rule = 参照されない文書。近縁の rule へ吸収)。新設場面(対象ファイルが未存在)の発火ギャップは上位の広い rule に 1 行のポインタで埋める。設計と経緯は [restructure-context.md](restructure-context.md)。
- **作業フォルダは docs/work/ で git 管理する(2026-08)**: 旧 root `work/`(gitignore)を `docs/work/` へ移し git 管理に変更(完了時に削除する一時物の性格は維持。履歴に残ることで仕様レビュー・worktree・別マシン再開・引き継ぎが成立)。ブランチ作業は `docs/work/<branch-slug>/`(`work-init` skill・任意)、小変更は直下フラット。中間フロー(/spec /plan /impl /review)は「ブランチフォルダ優先・無ければ直下」の解決規則(正は `docs/work/README.md`)だけに依存し、初期化・完了の有無に非依存。完了は `work-close` skill = 片付けがメイン(蒸留漏れ確認 → SPEC / PLAN 削除 → 最終プッシュ・ブランチ削除の提示。lite の spec-close を置換し、full の spec-close は SPEC 蒸留手順として存続)。途中プッシュ(他者レビュー)を含む git 操作の型は `git-commit` skill に一元化(提示のみ・実行は人、を維持)。
- **ADR と rules は独立して保管する(2026-08)**: `docs/adr` = 本来の ADR(なぜの履歴・不変・**手動編集が基本・作製タイミング任意**。`/adr` はドラフト支援)。`.claude/rules` = 決定の機械制約面(`rule-create` skill で追加)。**相互リンクは持たない**(rule に ADR-ID を書かない。発見はタグ・語彙の一致で足りる)。ADR の関連はメタデータで表す: `tags`(1〜3。語彙は rules ファイル名 → glossary)+ `related`(ADR 間)。`index.md` は frontmatter からの**生成物**(時系列 + タグ別。手編集しない)。ファイルはフラット連番を維持(サブディレクトリ・先頭数字グループは採らない: 事前分類の強制・複数所属不可・不変性との衝突のため)。**レビューが見るのは ADR 準拠**(rules は実装時に paths で効くため再確認しない)。/spec /plan /review に ADR 参照・準拠確認を組み込み、「書くだけで読まれない」経路を塞ぐ。
- **時刻の扱い(2026-08)**: `DateTime.Now` を直参照しない。業務の処理日時はリクエスト / 処理単位のコンテキストに**確定値として保持して参照**し(同一処理内で時刻を揺らさない)、「今」を確定する境界だけ `TimeProvider` を注入してテストで差し替える。
- **Worker は 2 様式(2026-08)**: ワンショット型(外部スケジューラ起動 + ExitCode 通知)を常駐型と対等な様式として worker rule に置く(選定は `/adr`)。周期実行は併記 — 既定 `PeriodicTimer`、ドリフトを避けたい高頻度・絶対時刻同期は「絶対時刻 next + 差分 Delay」方式。cron 周期ジョブは一般語化(ジョブ抽象 + cron は設定から)。
- **drafts 取り込みの残決定(2026-08)**: blazor = code-behind **常時分離**・rule は **Server / WASM 共通**・フォーム検証は規律のみ一般化(ライブラリは `/adr`)。mvvm = 「VM→View の単発要求 = Messenger / 継続的な購読・合成 = Rx」の 1 行を明文化。domain = Code の const は **DB 格納型と同型**(data の INTEGER 規約は新規設計時)・**Subcase = Usecase 層の DI 部品に限り、DI 不要は Logic に一本化**。testing = モックは NSubstitute を既定候補(手書きも可・統一は `/adr`)。ADR サンプル 4 本は adr-guide の references/ に見本として同梱(SAMPLE-01〜04・新形式)。`/review-cross` は存続(Claude 専用化はコンテキスト機構の話に限る)。作業フォルダの PreToolUse フックは見送り(backlog)。
- **skill 呼び出し時の git 実行(2026-08)**: `work-close` / `git-commit` skill の手順として人から明示的に依頼されたときは、**AI が git 操作を実行してよい**(push 等は permission の確認が入る)。AGENTS.md の一般規約(提示のみ・人が実行)は変更しない — skill の指示が呼び出し時のより具体的な指示として優先される。
- **ログレベルの定義と LoggerMessage 全面採用(2026-08)**: WARN = **想定内の異常**(コードが想定して備えた事象。発生は異常だが処理は継続する。想定していなければそもそも WARN を出す判断ができない)。ERROR = 出力箇所は**基盤部分が基本**(FW・ライブラリ制約による下層出力は例外として許容。中間のロジック層では直接扱わない)。ログ出力は `[LoggerMessage]` ソース生成を**全面採用**(直書き禁止)。命名 = レベル略称 + 事象、書式 = 英文 + `key=[{value}]`、配置は適宜分割(`Log.cs` 単一前提を緩和)。
- **文体**: ASCII / 括弧は半角、`§` 不使用、冗長・自明な括弧補足は書かない。ドキュメント・コメントは日本語。
