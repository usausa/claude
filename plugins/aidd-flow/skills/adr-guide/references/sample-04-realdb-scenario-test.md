> **サンプル ADR**(テスト戦略の記録例)。統合テストの方式はプロジェクト決定のため、決める場合はこの形で残す。

## 背景 / 課題

SQL 中心の設計(外部 2-way SQL + Micro-ORM。SAMPLE-01)では、データアクセスをモックした Service テストは肝心の **SQL・スキーマ整合を検証できない**。一方、業務フロー(注文 → 検証 → 採番 → 更新 → メール)の回帰を人手で確認するのは高コスト。統合テストの方式と、CI / 開発環境での実行条件を決める必要がある。

## 決定

**実 DB に対する API シナリオテスト**を統合テストとして採用する。

- `WebApplicationFactory` でアプリを起動し、HTTP で操作 → **応答 + DB 状態 + 送信メッセージ**を検証する
- フィクスチャは **CSV(テーブル名.csv)を Entity 型で投入**する
- **opt-in 機構**: 接続設定ファイルが存在するときだけ実行(無ければ自動 Skip)。**テスト専用の占有 DB を前提**とし README に明記する(テストの都度データを削除するため)
- 非決定要素は Factory で差し替える: `TimeProvider` 固定・メール送信のメモリ実装・外部 HTTP のダミー化
- テストはグループ直列化する(同一 DB を共有するため)

## 検討した代替案

- **案A: Testcontainers で DB をテストごとに起動** / 却下理由: 対象 DB(商用 RDBMS)のコンテナが重く、既存スキーマ・初期データの構築時間が長い。Docker 前提を置けない環境がある。※軽量 DB の新規プロジェクトでは有力
- **案B: InMemory / SQLite 代替 DB** / 却下理由: 方言(ロック・関数・型)が本番と異なり、2-way SQL がそのまま動かない = 検証したいものが検証できない
- **案C: データアクセスをモックした Service テスト** / 却下理由: SQL とスキーマの回帰(このシステムの主要リスク)を検知できない

## 結果(トレードオフ・影響)

- **得たもの**: SQL・スキーマ・業務フローの回帰検知、フィクスチャの可読性(CSV = テーブルの写し)、環境が無い場所でも壊れないテストスイート(自動 Skip)
- **捨てたもの**: どこでも実行できる完全な自己完結性(占有 DB の準備が必要)、並列実行(直列制約)
- **将来への注意**: 時刻依存の業務(締め時刻・営業日)をテストするため、本体に `TimeProvider` 抽象を必須とする(`DateTime.Now` 直参照の禁止)
