> **サンプル ADR**(技術選定の見本)。実プロジェクトの決定を一般化したもの。利用時は採番・実日付にして `docs/adr/` へ。

## 背景 / 課題

DB アクセスの実装方式を決める必要がある。対象 DB には既存スキーマ(命名・型の癖を含む)があり、検索系は JOIN・動的条件・ページングを多用する。SQL の性能チューニングと DBA / 有識者による SQL 単体レビューを開発フローに組み込みたい。

## 決定

**Micro-ORM(Smart.Data.Accessor)+ 外部 2-way SQL ファイル**を採用する。

- データアクセスはインターフェースだけを書き、実装はコンパイル時生成
- SQL は外部ファイルに分離し、**バインド変数コメント + ダミー値の 2-way 形式**で SQL ツールにそのまま貼って実行・検証できる形を保つ
- DB 方言(重複キー判定・LIKE エスケープ)は方言ヘルパーに、型の癖は TypeHandler に隔離して境界吸収する

## 検討した代替案

- **案A: EF Core** / 却下理由: 生成 SQL の制御が難しく、既存スキーマの癖(複合キー・文字列日付列・チューニング済みクエリ)との相性が悪い。マイグレーションは DB が外部所管のため使えない
- **案B: Dapper(SQL 文字列を C# に埋め込み)** / 却下理由: SQL がリテラルに埋まり、単体レビュー・ツールでの実行・静的検査がしにくい。動的条件の組み立てが手続き的になる

## 結果(トレードオフ・影響)

- **得たもの**: SQL の完全な制御と可読性(そのまま実行できる)、チューニング・レビューのしやすさ、コンパイル時生成による型安全と低オーバーヘッド
- **捨てたもの**: LINQ によるクエリ合成、EF エコシステム(マイグレーション・変更追跡)。エンティティ追跡が無いため更新は明示的に書く
- **将来への注意**: SQL ファイル数は増える(機能単位の命名規約で管理)。統合テストは SQL を検証できる方式が必要になる(→ SAMPLE-04)
