# 例外・異常系の扱い

> .NET 共通の原則。**通知の具体形はアーキ固有**なので、採用形態の rule の「異常系の具体」を参照。

## 原則
- **アプリ層の異常系は例外に頼らず結果で通知する**。エラーコードと値が要るならタプル / 専用型。
- 予期せぬ例外は各所で握らず **Fail-fast**。グローバルに処理し、続行させない。
- 発生が予期できるものは例外を出さない書き方にする (`Parse` でなく `TryParse` 等)。

## 3 層戦略

| 層 | 手段 | 例 |
|---|---|---|
| 入力検証 | 宣言的バリデーション (システム境界で) | 桁・書式・必須 |
| 業務検証 | **結果で通知** (bool 戻り値 or エラー蓄積器) | 在庫不足・組み合わせ不可 |
| 想定外 | throw → **境界で一元変換** | DB 障害・バグ |

- 業務エラーの様式は規模で選ぶ: 失敗理由が 1 種で分岐が単純なら **bool 戻り値**、複数の検証結果をまとめて返すなら**エラー蓄積器** (エラー = 中断 / 警告 = 継続して応答に同梱)。
- 例外 throw による業務エラー通知は、**境界で一元変換できる場合に限る** (変換表は採用形態の rule)。
- null → 404 や権限のような定型ガードは**宣言的なガード拡張** (`MustExist()` 等) に統一し、if + throw を都度書かない。

## 個別 try/catch してよいケース
- ランタイムでしか検出できず、ライブラリが例外で通知するもののみ (DB の一意制約違反、外部 I/O のタイムアウト等)。

## 再throw の作法
- ログ出力だけして握りつぶさない。スタックトレースを潰さない。
- 一部条件だけ処理して再throw する場合は **`throw;`** (`throw ex;` にしない)。
