# 応用: AOP + DI 自動登録

| 項目 | 内容 |
|---|---|
| ID | generator-4 |
| 分類 | generator |
| 関連 | generator-1(プロジェクト構成と配布) / generator-2(実装作法) / generator-3(テスト方式) / host-4(DI 登録スタイル) / log-1(Log.cs 定型) / log-5(ログ4系統の個別トグル) / telemetry-1(OpenTelemetry) |

## 目的

ソースジェネレータの応用形として、**サービスの横断関心事(ログ・トレース)の Proxy 生成と、DI 登録コードの自動生成**を組み合わせる。

- サービス実装に `[Service]` を付けるだけで、メソッドの開始/終了ログ・トレースを差し込む Proxy と、DI 登録の1行が生成される
- 登録コードが属性から機械的に導出されるため、**「実装を書いたのに登録し忘れる」事故が構造的に起きない**
- 実行時リフレクション(DispatchProxy / Castle 等)を使わないため、AOT 互換でオーバーヘッドはログ・トレース出力分のみ

## 標準形

### 利用側 — 属性の宣言

サービス実装に `[Service(typeof(インターフェース))]` を付ける。

```csharp
namespace Template.Service.Services;

[Service(typeof(IDataService))]
public sealed class DataService : IDataService
{
    public async ValueTask<DataResult> QueryAsync(DataParameter parameter, CancellationToken cancellationToken)
    {
        // 業務処理のみを書く(ログ・トレースは書かない)
    }
}
```

登録の受け口は `[ServiceRegistry]` を付けた partial メソッドとして1箇所だけ宣言する。**宣言は `[Service]` を付けたサービス実装と同じプロジェクトに置く**(ジェネレータはコンパイル単位毎に走るため、走査対象・partial 宣言・生成実装は同一プロジェクトでなければ成立しない)。

```csharp
namespace Template.Service.Services;

public static partial class ServiceConfigurationExtensions
{
    [ServiceRegistry]
    public static partial IServiceCollection AddApplicationServices(this IServiceCollection services);
}
```

### 実行時ヘルパー — ServiceAspect / ServiceAspectOption

横断処理の実体は生成コードに埋め込まず、**手書きの `ServiceAspect<T>` に集約する**。生成 Proxy はこれへの委譲だけになり、生成コードが最小に保たれ、横断処理の変更にジェネレータの再ビルドが不要になる。

```csharp
public sealed class ServiceAspectOption
{
    public bool Enable { get; set; }

    public ActivitySource ActivitySource { get; set; } = default!;
}
```

`ServiceAspect<T>` は `ILogger<T>` と `ServiceAspectOption` を受け、開始 / 終了 / 例外の3操作を提供する。ログとトレースを一体で扱う。

```csharp
internal sealed class ServiceAspect<T>
{
    private readonly ILogger<T> log;

    private readonly ActivitySource activitySource;

    public ServiceAspect(ILogger<T> log, ServiceAspectOption option)
    {
        this.log = log;
        activitySource = option.ActivitySource;
    }

    // Start: 開始ログを出力し、ActivitySource から Activity を開始する。
    //        経過時間計測の起点は AsyncLocal に保持し、非同期メソッドを跨いで Finish / Exception に引き継ぐ
    public void Start(string name) { /* ... */ }

    // Finish: Activity を終了し、経過時間付きの終了ログを出力する
    public void Finish(string name) { /* ... */ }

    // Exception: Activity にエラーステータスと例外を記録し、例外名・経過時間付きの終了ログを出力する
    public void Exception(string name, Exception ex) { /* ... */ }
}
```

- ログ出力は `[LoggerMessage]` 定型(log-1)。書式は `Service start. method=[{method}]` / `Service end. method=[{method}], elapsed=[{elapsed}]` の形とし、文字列補間ログを作らない

### 生成側 — Proxy クラス

ジェネレータは `[Service]` 対象毎に、同一インターフェースを実装する Proxy を生成する。Proxy は `ServiceAspect<T>` への通知と実体への委譲のみを行う。

```csharp
// <auto-generated />
namespace Template.Service.Services;

internal sealed class DataServiceProxy : IDataService
{
    private readonly ServiceAspect<DataService> aspect;

    private readonly DataService target;

    public DataServiceProxy(ServiceAspect<DataService> aspect, DataService target)
    {
        this.aspect = aspect;
        this.target = target;
    }

    public async ValueTask<DataResult> QueryAsync(DataParameter parameter, CancellationToken cancellationToken)
    {
        aspect.Start(nameof(QueryAsync));
        try
        {
            var result = await target.QueryAsync(parameter, cancellationToken).ConfigureAwait(false);
            aspect.Finish(nameof(QueryAsync));
            return result;
        }
        catch (Exception ex)
        {
            aspect.Exception(nameof(QueryAsync), ex);
            throw;
        }
    }
}
```

- 再スローは `throw;` でスタックトレースを保つ(guideline-1)

### 生成側 — 登録メソッドの実装

`[ServiceRegistry]` の partial メソッド実装として、全 `[Service]` 対象の `AddSingleton` を生成する。実体と Proxy の両方を登録し、インターフェースは `ServiceAspectOption.Enable` により実体直結 / Proxy 経由を実行時に切り替える。

```csharp
// <auto-generated />
namespace Template.Service.Services;

public static partial class ServiceConfigurationExtensions
{
    public static partial IServiceCollection AddApplicationServices(this IServiceCollection services)
    {
        services.AddSingleton<DataService>();
        services.AddSingleton<IDataService>(static p =>
            p.GetRequiredService<ServiceAspectOption>().Enable
                ? new DataServiceProxy(p.GetRequiredService<ServiceAspect<DataService>>(), p.GetRequiredService<DataService>())
                : p.GetRequiredService<DataService>());

        // 以下、[Service] を付けた全サービスが同じ形で列挙される

        return services;
    }
}
```

- 生成の仕組み自体は generator-2 の作法に従う: `ForAttributeWithMetadataName` で `[Service]` / `[ServiceRegistry]` を収集し、`internal sealed record` の model に落として `Combine` で合流、`SourceBuilder` で組み立てる

### ホスト側 — Aspect の構成と登録の呼び出し

host-4 の `ConfigureComponents()` から、Aspect の構成と生成された登録を呼ぶ。有効化トグルは Invoke トレースのログトグル(log-5)から、`ActivitySource` は `ApplicationInstrument`(telemetry-1)から与える。**本番はトレース ON、性能検証時は OFF のように、ビルドし直さず構成で切り替え**られる。

```csharp
// Service
builder.Services.AddServiceAspect(static (p, option) =>
{
    option.Enable = p.GetRequiredService<LogSetting>().InvokeTrace;
    option.ActivitySource = p.GetRequiredService<ApplicationInstrument>().ActivitySource;
});
builder.Services.AddApplicationServices();
```

`AddServiceAspect` は `ServiceAspectOption` と `ServiceAspect<>` を DI 登録する手書きの拡張メソッド。

```csharp
public static IServiceCollection AddServiceAspect(this IServiceCollection services, Action<IServiceProvider, ServiceAspectOption> configure)
{
    services.AddSingleton(p =>
    {
        var option = new ServiceAspectOption();
        configure(p, option);
        return option;
    });
    services.AddSingleton(typeof(ServiceAspect<>));

    return services;
}
```

## 配置ルール

| 対象 | 場所 |
|---|---|
| `ServiceAttribute` / `ServiceRegistryAttribute` / `ServiceAspect<T>` / `ServiceAspectOption` | サービス実装側プロジェクトの `Services/Aspect/`。汎用ライブラリとして配布する場合は本体ライブラリへ(generator-1: 属性は本体同居) |
| ジェネレータ本体 | アプリ内の Generator プロジェクト(`OutputItemType="analyzer"` の ProjectReference = generator-3 の参照形)。汎用配布時はパッケージ化(generator-1) |
| Proxy / 登録メソッドの生成コード | ジェネレータ出力(`.g.cs`) |
| `[ServiceRegistry]` partial メソッドの宣言 | サービス実装と同じプロジェクトの登録拡張クラス(host-4 の `AddXxx()` パターン) |
| `[Service]` 属性 | 各サービス実装(`Services/` / `Usecase/`)に付与 |

## バリエーションと使い分け

- **手動登録との併用**: 自動登録は `[Service]` を付けた層(Service / Usecase)に限定し、Provider・Component 等の少数の部品は host-4 の手動登録のまま残す。`ConfigureComponents()` のレイヤ順の見た目は維持する
- **ログのみへの簡略化**: トレースが不要な場合は `ServiceAspect<T>` から Activity を外し、ログのみとする。Proxy・登録の生成形は変わらない
- **ライフタイムの指定**: 既定は Singleton(host-4)。例外的なライフタイムは属性引数(`[Service(typeof(I), Lifetime = ...)]`)で宣言し、登録生成側で反映する
- **採用基準**: サービス数が少なく開始/終了ログも不要なうちは導入しない。「登録漏れが起きる規模」「全サービスに一律のログ/トレースが欲しい」のいずれかが成立してから導入する

## アンチパターン

- **実行時リフレクションによる AOP** — DispatchProxy・動的プロキシは AOT 非互換で実行時コストもかかる。生成で解決する
- **アセンブリスキャンによる自動登録** — リフレクションでの型走査は AOT・トリミングと相性が悪く、登録対象が実行してみるまで分からない。生成コードなら登録一覧がソースとして見える(部品表 = host-4 の思想を保つ)
- **Proxy への業務ロジック混入** — 生成 Proxy は横断関心事のみ。業務判断を入れたくなったらそれは Decorator として手書きする
- **手動登録と自動登録の二重管理** — 同一サービスを `AddApplicationServices()` と手動 `AddSingleton` の両方で登録しない。`[Service]` を付けたものは自動登録に一本化する
- **ログの二重出力** — Proxy が開始/終了ログを出すサービスの内部で、同じ粒度の開始/終了ログを手書きしない(業務イベントのログのみ書く)
